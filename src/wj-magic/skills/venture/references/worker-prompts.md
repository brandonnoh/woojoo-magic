# 워커 프롬프트 템플릿 — 발굴용 / 심문용

워커는 `Agent` 툴로 병렬 fan-out한다(`run_in_background: true`). 3~5명(O4).
Orca 오케스트레이션이 있으면 그쪽을 쓴다 — 독립 세션이라 WebSearch 예산이 리셋된다.

## 모든 워커에 공통으로 주입할 것

아래 4줄은 **템플릿과 무관하게 항상** 넣는다.

```
- 결론을 미리 정하지 말고 사실만 확인하라. 홍보 문구와 실측을 구분해 표기하라.
- 모든 수치·주장에 근거 등급을 붙여라: [실측] [문서] [자체발표] [추정] [미검증]
  가능하면 curl·API 호출·파일 다운로드로 직접 확인하고 [실측]으로 표기하라.
- 검색은 핵심 사실 확인에 집중하라. 예산이 없으면 추측하지 말고 [미검증]으로 명시하라.
- 낙관 금지. 이 방향이 안 되는 근거(반대 신호)도 반드시 찾아라.
```

## 템플릿 1 — 발굴용 (DISCOVER / DESIGN)

```
**결론을 미리 정하지 말고 발굴하라. 홍보 문구와 실측을 구분해 표기하라.**

## 조사 질문
{한 문장}

## 창업자의 실제 자산
{보유 기술 / 이미 만든 것 / 네트워크 / 자본 / 가용 시간 / 도메인 경험}

## 확인할 것
{번호 목록. 각 항목에 검증 방법 명시}
{반대 신호를 찾는 항목 최소 1개 포함}

## 공통 실격 필터
{프로젝트 공통 조건 — filters.md의 실격 필터}

## 산출
**{경로}에 Write로 저장하라. 저장이 최우선이다.**
구체 아이템 3개를 제안하되 반드시 6필드 형식으로:
(a) 한 문장 정의 (b) 첫 고객과 접촉 경로(채널 실명) (c) 첫 매출까지 걸리는 시간
(d) 가격(구체 금액) (e) 실격 필터 통과 여부(항목별 판정) (f) 3년 뒤 낙관/비관 시나리오
**탈락시킨 후보와 그 이유도 표로 남겨라.**
저장 후 응답에는 아이템 3개 이름 + 각 한 줄 근거만.
```

## 프롬프트 작성 원칙

**저장 지시는 산출 항목의 첫 줄에 둔다(O1).** 맨 끝에 두면 무시된다.
긴 리포트를 응답으로 받지 마라 — 잘려서 회수에 턴이 낭비된다.

**명제로 분할한다(B2).** 워커 5명에게 "PM 관점", "UX 관점"을 주면 비슷한 시장조사가
5개 나온다. 대신 각 워커에게 **서로 다른 명제 하나씩**을 준다:

- ❌ "마케팅 관점에서 분석해줘"
- ✅ "'이 타겟은 커뮤니티에서만 유입된다'는 판단이 참인지 확인하라"

**검증 방법을 지정한다.** "조사하라"가 아니라 "개발자 문서를 열어 엔드포인트 목록을
확인하고, 실제로 curl로 호출해 응답 스키마를 붙여라"처럼 쓴다. 이 한 줄이 [자체발표]를
[실측]으로 바꾼다.

## 실패 대응

**조기 종료** — 워커가 도구 호출 0회로 멈추면(생각만 하고 종료) 반드시 재개시킨다:
> "너는 아직 도구를 한 번도 호출하지 않았다. 지금부터 실제로 WebSearch/WebFetch/Bash(curl)를
> 여러 번 호출해 끝까지 수행하고, 지정 경로에 저장한 뒤 판정 1줄 + 근거 3줄을 반환하라."

**저장 누락** — 응답만 오고 파일이 없으면 재개시켜 저장부터 시킨다. 응답 본문을
코디네이터가 대신 저장하지 마라(잘린 내용을 확정시키게 된다).

**검색 예산 소진** — WebSearch가 막히면 WebFetch로 우회
(`url="https://html.duckduckgo.com/html/?q=<검색어>"`). 코디네이터는 자기 검증용으로
**최소 20회를 남긴다**(O2). 워커에게 배정할 때 라운드당 총 예산을 명시하면 좋다.

**결과 회수** — 워커 완료 통지를 받으면 저장된 파일을 읽어 종합한다.
리포트 원문은 SHIP 단계에서 `docs/reports/`로 정리한다.
