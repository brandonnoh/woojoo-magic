# Venture — 만들고, 즉시 부수고, 살아남은 것만 남긴다

**목적은 아이디어를 만드는 것이다.** 심문은 목적이 아니라 아이디어 품질을 올리는 장치다.

이 스킬은 한 방향으로 흐르는 파이프라인이 아니라 **루프**다. 아이디어가 실측을 견딜 때까지 돈다.

```
        ┌──────────────────────────────────────┐
        ↓                                      │
    발굴(DISCOVER) → 심문(INTERROGATE) → 죽음 ──┘
        ↓                    ↓
        └────────→ 생존 → 설계(DESIGN) → 종합(SYNTHESIZE)
                              ↑                  │
                              └─── 전제 깨지면 ───┘
```

심문 결과가 전제를 깨면 **자동으로 발굴로 되돌아간다.** 한 번 돌고 끝나지 않는다.

## 왜 이렇게 생겼는가 — 실패에서 나온 설계

직군 기반 5인 스쿼드(PM/UX/사업/마케팅/데이터)가 리포트를 내면 그게 곧 결론이 됐다.
아무도 그 리포트의 전제를 확인하지 않았다. 결과는 "그럴듯한데 허약한 아이디어"다.

실제 사례: 원본 기획서가 "플랫폼이 이미 흡수했으니 이 사업은 안 된다"며 1순위 아이템을
배제했는데, **개발자 문서를 한 번도 열어본 적이 없었다.** 나중에 워커가 curl 한 번 쳐보니
사업 방향 전체가 뒤집혔다.

그리고 실사용에서 "발굴"과 "검증"의 경계는 존재하지 않았다. 조사는 이렇게 흘렀다:

> 스쿼드로 전략 확정 → 심문했더니 전제가 깨짐 → 축을 다시 발굴 → 또 깨짐
> → 실측으로 원본 전제 붕괴 → 다시 발굴 → 마침내 살아남는 아이디어 도달

별개 스킬이 아니라 한 루프의 단계였다. 그래서 하나로 합쳤다.

## 4개 모드 — 진입 시 자동 판별

사용자에게 **"무슨 모드로 할까요"를 묻지 마라.** 입력을 보고 판별한 뒤 선언하고 시작한다.
판별 기준 상세 → [references/modes.md](references/modes.md)

| 모드 | 진입 조건 | 하는 일 |
|---|---|---|
| **DISCOVER** | 아이템이 없거나 후보 중 미정 | 후보를 넓게 발굴 → 실격 필터로 대부분 죽이고 살아남은 것만 남김 |
| **DESIGN** | 아이템 확정, 구체화 필요 | 다각도 병렬 리서치 → 통합 스펙·로드맵·감각 방향 |
| **INTERROGATE** | 이미 내려진 판단·전제가 있음 | 그 판단이 실제로 참인지 실측으로 심문 |
| **SYNTHESIZE** | 리포트 2개 이상 축적 | 교차 검증 → 일치/충돌/뒤집힌 것 정리 |

선언 형식: `모드: DISCOVER — 아이템 미정이므로 후보 발굴부터 시작한다.`

**모드는 고정이 아니다.** INTERROGATE가 전제를 깨면 DISCOVER로, DESIGN 중 전제가 흔들리면
INTERROGATE로 즉시 전이한다. 전이할 때마다 사용자에게 한 줄로 알린다.

## 만들기 장치 5개 — 쓸 수 있는 아이디어가 나오게

### M1. 아이템 제안은 6필드 형식을 강제한다
워커가 "이런 방향이 좋겠다" 같은 추상적 제안을 내지 못하게 막는 장치다.
모든 아이템 제안은 반드시:

**(a)** 한 문장 정의 · **(b)** 첫 고객이 누구이고 어떻게 찾는가(채널을 실명으로) ·
**(c)** 첫 매출까지 걸리는 시간 · **(d)** 가격(구체 금액) ·
**(e)** 실격 필터 통과 여부(항목별 판정) · **(f)** 3년 뒤 낙관/비관 시나리오

이 형식이 아이디어를 "말"에서 "실행 가능한 것"으로 바꾼다. 실제로 이 형식을 강제했더니
워커가 *"안전인증 컴플라이언스 봇, 현장당 월 5~15만원, 첫 매출 6~8주, KOSHA 오픈API 3종
실존(검증됨)"*까지 내놨다. 형식 명세 → [references/contracts.md](references/contracts.md)

### M2. 창업자의 실제 자산을 워커에게 알려준다
"1인 창업자" 같은 추상적 설정이 아니라, **실제로 무엇을 할 줄 아는지** 구체적으로 넣는다.
보유 기술 / 이미 만든 것 / 네트워크 / 자본 / 가용 시간 / 도메인 경험.

이 입력이 없으면 교과서적 아이템만 나온다. **진입 시 자산을 모르면 딱 한 번, 6항목을
묶어서 묻는다**(질문을 몰아치지 않는다 — O 규칙). 사용자가 모른다고 하면 리포지토리·
이력·이전 프로젝트에서 추론해 초안을 만들고 확인만 받는다.

### M3. 탈락시킨 것과 그 이유도 쓰게 한다
"왜 그 아이디어가 아닌지"가 "왜 이 아이디어인지"만큼 중요하다.
나중에 같은 후보가 다시 떠오를 때 재조사 비용을 없앤다. 워커 리포트에 **탈락 후보 표**를
필수 포함시킨다.

### M4. 반대 신호를 반드시 찾게 한다
**"사업이 안 되는 근거도 찾아라"**를 프롬프트에 명시한다.
실제로 이 지시 덕에 *"AI 트래픽을 차단하는 방향으로 시장이 움직인다"*는 결정적 반대 신호를
잡아냈고, 아이템 하나가 그 자리에서 죽었다. 확인 항목에 **반대 신호 탐색을 최소 1개** 넣는다.

### M5. 공통 실격 필터를 먼저 정의한다
프로젝트 상황에서 나온 실격 조건을 **모든 워커가 공유**한다.
(예: 고객당 수십 시간 온보딩 / 콜드콜이 매출의 전제 / 인허가 6개월+ / 재고·물류 선투자)

애초에 못 쓸 아이디어를 만들지 않게 하고, 서로 다른 축의 결과를 **같은 잣대로 비교
가능**하게 한다. 이게 없으면 종합이 불가능하다. 필터 카탈로그 →
[references/filters.md](references/filters.md)

## 부수기 장치 4개 — 허약한 아이디어를 걸러낸다

### B1. 근거 등급 표기를 강제한다 ← 이게 심장이다
```
[실측]   직접 호출·측정해 확인       [문서]   공식 문서 확인
[자체발표] 당사자 홍보 수치           [추정]   3자 추정      [미검증] 확인 못 함
```
프롬프트에 **"홍보 문구와 실측을 구분해 표기하라"**를 반드시 포함하고, 가능하면
curl·API 호출·파일 다운로드로 직접 확인하게 한다.

이 지시가 없으면 SEO 콘텐츠팜 수치를 그대로 믿는다. 실제로 *"$8B ARR"*이 다른 소스에선
$2.5B였고, *"$2B ARR"*은 실질 순매출이 3분의 1이었다. **판단을 뒤집은 것은 전부 실측이었다.**

### B2. 워커를 직군이 아니라 "검증할 명제"로 분할한다
- ❌ 나쁨: "PM 관점에서 분석해줘" → 5명이 비슷한 시장조사를 중복 생산
- ✅ 좋음: "'플랫폼이 이미 흡수했다'는 판단이 참인지 확인하라"

고정 5인 롤(PM/UX/마케터/데이터)은 명제 분할과 다르다. DESIGN 모드에서 다각도가 필요할
때도 **축은 명제로 쓴다**("이 가격대에서 지불 의사가 실재하는가?" 같이).
축 카탈로그 → [references/design-axes.md](references/design-axes.md)

### B3. 판정을 한 문장으로 강제한다
리포트 **§0에 판정을 먼저** 쓴다.

> 판정: {명제}는 ({A} / {B} / {판단 불가}).

양비론 금지. 모르면 "판단 불가"라고 쓰게 한다.
이게 없으면 리포트 5,000줄을 읽고도 결정을 못 한다.

### B4. 교차 검증을 SYNTHESIZE의 핵심으로 삼는다
- 워커 간 **독립적으로 일치한 결론** → 신뢰도 최상
- **충돌하는 결론** → 어느 쪽 근거 등급이 높은지로 판정([실측] > [문서] > [자체발표] > [추정])
- **원본 판단 대비 뒤집힌 것** → 별도 목록으로 명시

두 워커가 서로 모르는 채 같은 리스크를 1순위로 지목한 것이 실제 조사에서 가장 신뢰할 만한
결론이었다. 규약 → [references/contracts.md](references/contracts.md)

## 운영 규칙 4개 — 실패에서 나온 것

### O1. 파일 저장 최우선, 응답은 3줄
워커는 리포트를 **지정 경로에 Write로 먼저 저장**하고, 응답에는 **판정 1줄 + 근거 3줄**만
반환한다. 저장 지시는 프롬프트 맨 끝이 아니라 **산출 항목의 첫 줄**에 둔다.

> 실패 사례: 긴 리포트를 응답으로 반환시켰더니 5개 중 일부가 잘려 회수에 여러 턴이 낭비됐다.

### O2. 웹 검색 예산을 관리한다
워커 4~5명이 병렬로 돌면 세션 검색 한도(기본 200회)를 금방 태운다.
워커 프롬프트에 **"검색은 핵심 사실 확인에 집중하고, 예산이 없으면 미검증으로 명시하라"**를
포함한다. 코디네이터는 자기 검증용으로 **최소 20회를 남긴다.**

> 실패 사례: 워커들이 200회를 다 써서 코디네이터가 핵심 API 하나를 확인 못 했다.

### O3. 폐기된 방향은 삭제하지 말고 `docs/_archive/`로 옮긴다
판단 근거가 자산이다. 나중에 같은 후보가 떠오를 때 "이미 검토했고 이래서 접었다"가 남는다.

### O4. 워커 수는 3~5명. 그 이상은 중복이다
명제가 5개를 넘으면 **라운드를 나눠서** 돌린다.

## 모드별 실행

공통 절차: **① 모드 판별·선언 → ② 창업자 자산·실격 필터 확정(M2·M5) → ③ 명제 3~5개로
분할(B2) → ④ 워커 병렬 fan-out → ⑤ 리포트 회수·판정 종합 → ⑥ 루프 판단.**
워커 프롬프트 템플릿 2종 → [references/worker-prompts.md](references/worker-prompts.md)

### DISCOVER — 발굴
넓게 벌린 뒤 실격 필터로 죽인다. 후보를 한두 개로 일찍 좁히지 않는다(이른 깊이 = 확증 편향).

1. 각도를 나눠 워커 배치 — 세그먼트/버티컬/벤치마크 시장/창업자 자산 역산.
2. 각 워커는 **6필드 아이템 3개 + 탈락 후보 표**(M1·M3)를 낸다.
3. 코디네이터가 실격 필터·킬러 필터로 판정 → 생존 1~3개.
4. 생존 아이템의 **핵심 전제를 명제로 뽑아 즉시 INTERROGATE**로 넘긴다.

### DESIGN — 설계
아이템이 확정된 뒤 구체화한다. 이 모드가 기존 `ideation`을 흡수한 자리다.

1. 명제형 축 3~5개로 병렬 리서치(`design-axes.md`의 축 카탈로그 사용 — **직군이 아니라 명제로**).
2. 통합 산출: 최종 스펙 · 설계 원칙 · 수익화 구조 · 기술 아키텍처 · 그로스 · 규제 · MVP 로드맵.
3. 감각·인격·디자인 토큰이 필요하면 [references/craft.md](references/craft.md)로 anti-slop 방향 정의.
4. 리서치 도중 **전제가 흔들리면 즉시 INTERROGATE로 전이**한다(설계를 끝까지 밀지 않는다).

### INTERROGATE — 심문
이미 내려진 판단을 실측으로 확인한다. **결론을 미리 정하지 않는다.**

1. 검증할 명제를 인용문으로 고정하고 "이 판단은 언제, 무엇을 근거로 내려졌는가"를 명시.
2. 워커에게 **검증 방법을 지정**한다 — "실제 문서를 열어봐라", "직접 호출해봐라", "다운로드해봐라".
3. 각 워커는 §0 판정 문장(B3) + 근거 등급 표기(B1)로 리포트.
4. **전제가 깨지면 → DISCOVER로 되돌아간다.** 이건 실패가 아니라 이 스킬의 정상 동작이다.

### SYNTHESIZE — 종합
리포트 2개 이상이 쌓이면 교차 검증한다(B4).

1. 일치 / 충돌 / 뒤집힘 3개 목록으로 분류.
2. 충돌은 근거 등급으로 판정하고, 판정 불가면 추가 실측 명제를 만들어 INTERROGATE 1라운드.
3. 통합 문서 개정 — **이전 판단과 무엇이 바뀌었는지 표로**(원본 대비 변경 N건).

## 종료 조건

다음을 모두 만족하면 루프를 끝내고 SHIP(정리)로 간다.

- 승자 아이템의 6필드가 **전부 [실측] 또는 [문서] 등급**으로 채워졌다.
- 직전 **2라운드 연속 전제 붕괴가 없었다.**
- 반대 신호(M4)를 찾았고, 그것을 안고도 판정이 유지된다.

하나라도 미달이면 남은 명제로 라운드를 한 번 더 돈다.

## SHIP — 정리 (종료 시 필수)

1. 워커 리포트·통합 문서를 `docs/`에 배치, 폐기 방향은 `docs/_archive/`로 이동(O3).
2. **8-bit 시각 리포트 생성 + 로컬 오픈 (필수)** — `../../references/common/REPORT_8BIT.md`
   가이드대로 `docs/reports/venture-{아이템}-8bit.html`을 생성하고 `open`으로 띄운다.
   STAGE 구성 예: 후보 도감(6필드 카드 그리드) → 실격 필터 게이트(생존/폐기 사유) →
   심문 판정 HUD(근거 등급별) → 뒤집힌 판단 목록 → 승자 딥다이브 → 다음 액션.
3. 사용자 피드백에서 취향·판단 기준을 읽으면 메모리에 저장한다(feedback 타입).

## 산출물 규약

- 워커 리포트: `docs/reports/{모드코드}{번호}-{주제}.md` (예: `A1-platform-reality.md`) — **§0은 항상 판정 먼저**
- 통합 문서: `docs/{번호}-strategy.md` (버전 표기)
- 개정 시 이전 판단과의 차이를 표로 명시
- 폐기 방향: `docs/_archive/`

모드코드: DISCOVER=`D` · DESIGN=`S` · INTERROGATE=`A` · SYNTHESIZE=`X`

## 관련 스킬과의 관계

- `brainstorm` — 아이템이 정해진 뒤 1:1 대화로 스펙 정제.
- `plan` — 스펙 확정 후 태스크 분해.
- `design` / `polish` — UI를 실제로 만들거나 다듬을 때(venture는 방향까지만).
- `db-design` / `devrule` — 구현 단계.

venture는 이들의 **앞단** — "무엇을 만들지, 그리고 그 판단이 진짜인지"를 담당한다.
