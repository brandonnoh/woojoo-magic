# 폴리글랏 DB 선택 가이드 — 결정 트리

> 워크로드를 먼저 분석해 각각에 **진짜 최적인 DB**를 매칭한다(디폴트 DB 없음). DB 추가의 운영 비용은 성능·적합성 이득과 저울질하되, 이득이 크면 처음부터 폴리글랏도 권고한다. 이 문서는 db-design 스킬의 심장 — 유형 카탈로그 → 결정 트리 → CAP/PACELC → 정합성 전략 순으로 판단한다.

## 0. 핵심 원칙 (워크로드 최적 우선 — Workload-First)

- **워크로드를 먼저 분석하고, 각 워크로드에 진짜 최적인 DB를 매칭한다.** 특정 DB를 디폴트로 깔고 시작하지 않는다. 트랜잭션·캐시·검색·추천·분석·시계열을 각각 뜯어 접근 패턴·일관성 SLA·지연 예산·규모를 보고, 그에 가장 맞는 유형을 고른다. **서비스 특성상 처음부터 폴리글랏이 최적이면 그렇게 권고한다** — "최소 개수"가 목표가 아니라 "최적 적합"이 목표다.
- **PostgreSQL은 "강력한 기본 후보"이지 자동 결론이 아니다.** PG 하나가 관계형·JSON(JSONB)·전문검색(tsvector/`pg_trgm`)·벡터(pgvector+pgvectorscale)·큐(`SKIP LOCKED`)·지리(PostGIS)·시계열(파티셔닝/TimescaleDB)·pub/sub(`LISTEN/NOTIFY`)를 **"충분히 좋게"** 커버하므로, 각 워크로드에서 "PG로 여기까지 되는가"를 **기준선(baseline)** 으로 검증한다. 임계를 넘거나 애초에 PG가 약한 영역이면 특화 DB를 매칭한다. (2025년 Instacart는 검색을 ES→PG+pgvector로 이관해 비용 80%↓ — 반대로 대규모 벡터·랭킹·전문검색이 핵심 가치인 서비스라면 처음부터 전용 스토어가 정답이다.)
- **두 실패를 동시에 경계한다.** ① **조기 폴리글랏** — 추측성 "확장성 위해" 도입(가장 흔한 오버엔지니어링). ② **PG-도그마** — 워크로드가 명백히 특화 DB를 요구하는데 유행 따라 억지로 PG에 밀어넣기. 판단 근거는 유행이 아니라 **아래 카탈로그·결정 트리의 워크로드별 임계값**.
- **폴리글랏의 진짜 비용은 성능이 아니라 정합성·운영.** DB를 하나 늘리면 백업·모니터링·장애 런북·동기화 파이프라인(CDC/이벤트/캐시무효화)이 함께 늘어난다(**N개 DB = N-1개 동기화 버그 표면**). 이 운영 비용을 **성능·적합성 이득과 저울질**해, 이득이 비용을 넘을 때만 추가한다 — 넘으면 주저 없이 추가한다.
- **SoT(Source of Truth)를 반드시 하나만 지정.** 나머지는 전부 **파생 저장소(projection)** 로 취급하고, 쓰기는 SoT로만 → CDC/이벤트로 비동기 전파. 이중 쓰기(dual-write) 금지.

## 1. 10종 DB 유형 카탈로그

각 유형: 대표 제품 / 핵심 / Best For / 트레이드오프 / **피해야 할 상황**.

### ① 관계형 (Relational)
| | |
|---|---|
| **제품** | PostgreSQL(디폴트), MySQL, SQL Server, CockroachDB(분산), Aurora |
| **핵심** | ACID 트랜잭션·강일관성·JOIN·제약(FK/UNIQUE/CHECK)·SQL |
| **Best For** | 뱅킹·이커머스·주문·재고·정산 — **돈·상태·불변식이 걸린 모든 것** |
| **트레이드오프** | 수평 확장이 가장 어려움(샤딩 복잡). 유연 스키마 아님(마이그레이션 필요) |
| **피해야** | 스키마가 요청마다 제각각인 반정형 로그, 초당 수백만 단순 쓰기 |

### ② 문서 (Document)
| | |
|---|---|
| **제품** | MongoDB, CouchDB, Firestore, DynamoDB(Document 모드) |
| **핵심** | 유연 스키마·중첩 JSON·집계(aggregation pipeline)·수평 샤딩 내장 |
| **Best For** | CMS·카탈로그·이벤트/설정처럼 **스키마가 자주 변하거나 문서가 통째로 조회**되는 워크로드 |
| **트레이드오프** | 다문서 트랜잭션 비싸고 제한적. JOIN 약함(비정규화·중복 감수). 스키마 없음=검증 책임이 앱으로 |
| **피해야** | 복잡한 다대다 JOIN, 강한 참조 무결성이 핵심인 금융. **"관계형이 애매해서 Mongo" 는 대부분 오판 — PG의 JSONB가 대안** |

### ③ 키-값 (Key-Value)
| | |
|---|---|
| **제품** | Redis, DynamoDB, Memcached, etcd, Valkey |
| **핵심** | O(1) 조회·초저지연·단순 데이터 모델 |
| **Best For** | 캐시·세션·rate limit·피처 플래그·리더보드(Redis Sorted Set)·분산 락 |
| **트레이드오프** | 쿼리 = 키 조회뿐(범위·필터 약함, DynamoDB는 GSI로 보완). 관계·집계 없음 |
| **피해야** | 애드혹 분석, 키를 모르는 탐색 쿼리, 복잡한 관계 데이터 |

### ④ 와이드컬럼 (Wide-Column)
| | |
|---|---|
| **제품** | Cassandra, ScyllaDB, HBase, Bigtable |
| **핵심** | 수십억 행·초고쓰기·선형 확장·마스터리스(무중단) |
| **Best For** | 이벤트/센서/로그/메시지 히스토리 — **쓰기 폭주 + 알려진 파티션 키로만 조회** |
| **트레이드오프** | 쿼리를 테이블 설계 전에 확정해야(query-first). JOIN·애드혹 없음. 최종일관성 기본. 운영 난도 높음 |
| **피해야** | 트랜잭션, 유연한 조회 패턴, 소규모(오버엔지니어링). **50M행 미만이면 PG 파티셔닝으로 충분** |

### ⑤ 그래프 (Graph)
| | |
|---|---|
| **제품** | Neo4j, Amazon Neptune, ArangoDB, PG+Apache AGE |
| **핵심** | 노드·엣지 1급 시민, **다중 홉 순회가 JOIN보다 압도적으로 빠름** |
| **Best For** | 소셜 그래프·추천·이상탐지(자금세탁)·권한 그래프·지식그래프 — **관계 순회 자체가 질문**일 때 |
| **트레이드오프** | 별도 쿼리 언어(Cypher/Gremlin). 단순 CRUD엔 과함. 대규모 쓰기 확장 까다로움 |
| **피해야** | 2홉 이하 관계(PG JOIN이면 충분), 집계 중심 분석 |

### ⑥ 시계열 (Time-Series)
| | |
|---|---|
| **제품** | TimescaleDB(PG확장), InfluxDB, Prometheus(모니터링), ClickHouse(분석형) |
| **핵심** | 시간 인덱스·자동 파티션(chunk)·압축(90%↓)·다운샘플링·retention 정책 |
| **Best For** | 메트릭·IoT 센서·금융 틱·모니터링 — **append-only + 시간 범위 쿼리** |
| **트레이드오프** | update/delete 비효율(설계상). 관계 모델 아님 |
| **피해야** | 트랜잭션 워크로드. **초기엔 PG 네이티브 파티셔닝으로 시작 → 삽입/쿼리가 무너지는 ~50M행·수십만 rows/s에서 TimescaleDB 전환**(TimescaleDB는 그 지점에서 삽입 20배·삭제 2000배) |

### ⑦ 검색 (Search)
| | |
|---|---|
| **제품** | Elasticsearch, OpenSearch, Solr, Typesense, Meilisearch, Atlas Search, Algolia(관리형) |
| **핵심** | 역색인·전문검색·랭킹(BM25)·패싯·오타보정·형태소 분석 |
| **Best For** | 상품/문서 검색, 로그 분석(ELK), 자동완성, 관련도 랭킹이 핵심인 UX |
| **트레이드오프** | SoT 부적합(근사·최종일관성). 정확한 카운트·트랜잭션 약함. 운영·리소스 무거움 |
| **피해야** | 소규모·단순 LIKE 검색. **PG `pg_trgm`+GIN / `tsvector`로 시작 → 랭킹·패싯·다국어 형태소·수천만 문서에서 ES/Typesense 추가** |

### ⑧ 벡터 (Vector)
| | |
|---|---|
| **제품** | pgvector(+pgvectorscale), Pinecone, Weaviate, Milvus, Qdrant |
| **핵심** | 고차원 임베딩 ANN 검색(HNSW/IVFFlat)·시맨틱 유사도 |
| **Best For** | RAG·시맨틱 검색·추천·이미지/중복 탐지 — **의미 기반 유사도** |
| **트레이드오프** | 정확검색 아님(근사). 인덱스 빌드·메모리 비용. 임베딩 재생성 파이프라인 필요 |
| **피해야** | 이미 PG를 쓰는데 전용 벡터DB 조기 도입. **pgvector+pgvectorscale는 50M 벡터·99% recall에서 sub-100ms로 Pinecone/Qdrant급 — 메타데이터 필터·RLS·트랜잭션을 SQL로 함께 처리하는 이점이 커서 2026 디폴트. 억 단위·초당 수만 QPS·팀 분리에서만 전용 검토** |

### ⑨ 인메모리 (In-Memory)
| | |
|---|---|
| **제품** | Redis, Memcached, Valkey, Hazelcast |
| **핵심** | RAM 상주·마이크로초 지연·자료구조(list/set/zset/stream) |
| **Best For** | 초저지연 캐시·세션·실시간 카운터·pub/sub·큐(Redis Streams) |
| **트레이드오프** | 휘발성(영속성 옵션 있으나 RAM 비용). 데이터 크기가 RAM에 제약 |
| **피해야** | 영속 SoT, RAM보다 큰 데이터셋. **sub-ms가 하드요건 아니면 캐시는 PG로도 가능 — Redis 추가 전 재고** |

### ⑩ 데이터웨어하우스 (OLAP / DW)
| | |
|---|---|
| **제품** | Snowflake, BigQuery, Redshift, ClickHouse, Databricks |
| **핵심** | 컬럼 저장·MPP·대규모 스캔/집계·분석 최적화 |
| **Best For** | BI·리포팅·애드혹 분석 — **읽기 중심 대량 집계**(OLTP와 분리) |
| **트레이드오프** | 단건 조회·트랜잭션 부적합. 로딩 지연(배치/스트리밍 ETL). 비용은 스캔량 기반 |
| **피해야** | 운영 트랜잭션(OLTP), 실시간 단건 lookup. **분석은 OLTP DB에서 직접 돌리지 말고 replica/DW로 분리** |

## 2. 결정 트리 — 유스케이스 → DB

먼저 **"강일관성 트랜잭션이 필요한가?"** 를 묻고, 아니면 접근 패턴으로 분기한다.

```
Q1. 돈·재고·상태처럼 강일관성 트랜잭션이 핵심인가?
    └─ YES → 관계형(PostgreSQL). 이게 항상 SoT의 출발점.

Q2. (SoT는 정해졌다) 이 워크로드의 지배적 접근 패턴은?
 ├─ 키로 초저지연 조회(캐시·세션·카운터) ......... 키-값/인메모리(Redis)
 ├─ 관계 다중 홉 순회가 질문 자체(추천·이상탐지) ... 그래프(Neo4j/Neptune)
 ├─ 전문검색·랭킹·패싯·오타보정 .................. 검색(먼저 PG tsvector → ES/Typesense)
 ├─ 시맨틱 유사도·RAG(임베딩) ................... 벡터(먼저 pgvector → 전용)
 ├─ 시간범위 append-only 메트릭·IoT ............. 시계열(먼저 PG 파티션 → TimescaleDB)
 ├─ 초당 수십만+ 쓰기, 알려진 파티션 키만 조회 ... 와이드컬럼(Cassandra/Scylla)
 ├─ 스키마 요청마다 제각각·문서 통째 조회 ........ 문서(MongoDB) *또는 PG JSONB*
 └─ 대량 집계·BI·애드혹 분석(OLTP와 분리) ....... DW(Snowflake/BigQuery/ClickHouse)
```

| 유스케이스 | 1차 선택 | PG로 버티는 임계 → 전환 신호 |
|---|---|---|
| 트랜잭션·정산·재고 | **PostgreSQL** | — (SoT는 항상 여기) |
| 캐시·세션·rate limit | Redis | sub-ms 불필요면 PG로도 가능 |
| 잡 큐·태스크 | **PG `SKIP LOCKED`** | ~50k jobs/sec 넘거나 팀 간 공유 → Kafka |
| 이벤트 스트리밍·팀 간 데이터 교환 | Kafka/Redpanda | (PG는 단일 앱 큐까지만) |
| 전문검색·랭킹 | PG `tsvector`/`pg_trgm` | 다국어 형태소·패싯·수천만 문서 → ES/Typesense |
| RAG·시맨틱 | **pgvector** | 억 단위 벡터·초당 수만 QPS·팀 분리 → Pinecone/Milvus |
| 메트릭·IoT | PG 파티셔닝 | ~50M행/수십만 rows·s → TimescaleDB/InfluxDB |
| 추천·이상탐지 그래프 | Neo4j/Neptune | 2홉 이하면 PG JOIN으로 충분 |
| 로그 초고쓰기 | Cassandra/Scylla | 50M행 미만이면 PG로 충분 |
| BI·분석 | Snowflake/BigQuery | 소규모면 PG read-replica로 |

## 3. CAP / PACELC — 유형별 좌표

**CAP**: 네트워크 파티션(P) 시 일관성(C)과 가용성(A) 중 택1. **PACELC**: 파티션이 없는 평상시(E)에도 지연(L)과 일관성(C)을 저울질한다 — 실무에선 파티션은 드물고 **평상시의 L↔C 트레이드오프가 훨씬 자주 체감**된다.

| DB / 유형 | PACELC 분류 | 의미 |
|---|---|---|
| PostgreSQL(단일/동기복제) | **PC/EC** | 파티션·평상시 모두 일관성 우선. 동기 복제는 지연 대가 |
| MySQL(비동기 복제) | PC/EL | 파티션 시 일관성, 평상시엔 replica lag 허용해 지연 최소화 |
| Cassandra / ScyllaDB | **PA/EL** | 파티션 시 가용성, 평상시 저지연 우선(튜너블: `QUORUM`이면 EC로 이동) |
| DynamoDB | PA/EL(기본) | 최종일관성 기본, **강일관성 읽기는 옵션(비용 2배)** |
| MongoDB | 설정 의존 | `w:majority`+`readConcern:linearizable`→PC/EC, 완화하면 PA/EL |
| Redis(단일) | 캐시(비-SoT) | 복제는 비동기 → 장애 시 데이터 손실 가능. SoT로 쓰지 말 것 |
| Neo4j(코어) | CP 성향 | 강일관성 우선, 클러스터 가용성은 read-replica로 보완 |

**핵심**: 현대 DB 대부분은 **쿼리·연산 단위로 일관성 레벨을 튜닝**할 수 있다(Cassandra consistency level, Dynamo 강일관성 읽기, Mongo read/write concern). "이 DB는 CP다"가 아니라 **"이 쓰기·이 읽기는 어느 레벨이 필요한가"** 로 사고하라.

## 4. 일관성 모델 — 언제 무엇이 필요한가

| 모델 | 보장 | 필요한 곳 | 과하면 |
|---|---|---|---|
| **강일관성 (Strong / Linearizable)** | 쓰기 즉시 모두가 최신값 | 잔액·재고·좌석·유니크 제약 | 지연·처리량 손해 |
| **Read-your-writes** | 내 쓰기는 내가 바로 읽음 | 프로필 수정·글 작성 직후 화면 | primary read 라우팅(500ms) 비용 |
| **Causal** | 인과 순서 보존(댓글이 원글 뒤) | 스레드·채팅·협업 | 구현 복잡 |
| **최종일관성 (Eventual)** | 언젠가 수렴 | 피드·검색색인·좋아요 카운트·캐시 | 결제·재고엔 **금지** |

처방: **돈·불변식 = 강일관성(관계형 트랜잭션). 파생 뷰(검색·피드·집계) = 최종일관성 허용.** 사용자 "내 액션 직후 화면"은 read-your-writes만 보장하면 UX가 깨지지 않는다 — 전역 강일관성으로 오버슈트하지 말 것.

## 5. 폴리글랏 조합 패턴 (실전)

성장 단계별 최소 조합. **SoT는 항상 PostgreSQL**, 나머지는 파생.

| 단계 | 조합 | 정합성 전략 |
|---|---|---|
| **MVP** | PostgreSQL 단독 | 트랜잭션이 곧 정합성. 캐시·검색·큐 모두 PG 기능으로 |
| **성장** | PG + Redis | 캐시는 write-through 또는 **CDC 기반 무효화**. 세션·rate limit·큐(`SKIP LOCKED`) |
| **검색 강화** | PG + Redis + ES/Typesense | PG WAL → CDC → 검색 인덱스. ES는 절대 SoT 아님 |
| **AI/RAG** | + pgvector(대개 PG 안) | 임베딩을 PG에 두고 메타데이터 필터와 SQL로 결합. 전용 벡터DB는 억 단위에서만 |
| **대규모** | + Kafka + DW + (시계열/와이드컬럼) | Kafka=이벤트 백본, DW=분석 분리, 특화 DB=무너지는 워크로드만 |

**파생 저장소 동기화 3대 방식:**
1. **CDC (권장, 결합도 최소)** — Debezium이 PG WAL을 tail → Kafka → 컨슈머가 ES/캐시/DW 갱신. 앱 코드 변경 없이 모든 변경을 정확히 캡처.
2. **Outbox 패턴** — 비즈니스 변경과 이벤트를 **같은 트랜잭션**으로 `outbox` 테이블에 기록 → 릴레이가 발행. 이중 쓰기(dual-write) 문제 해결의 표준.
3. **캐시 무효화** — 쓰기 시 키 삭제(무효화가 갱신보다 안전) 또는 CDC로 무효화 이벤트 구독.

**규칙**: 파생 저장소는 언제든 SoT에서 **재구축 가능**해야 한다(rebuild 스크립트 유지). 파생이 유실돼도 SoT만 있으면 복구된다.

## 6. 안티패턴 (흔한 오판)

- **"NoSQL이 무조건 빠르다"** — NoSQL은 특정 접근 패턴에 최적화된 것이지 만능 고속이 아니다. 잘못된 파티션 키·핫스팟이면 관계형보다 느리다.
- **"MongoDB로 모든 걸"** — 관계·트랜잭션이 생기는 순간 앱에서 JOIN·정합성을 재구현하게 된다. 애매하면 PG + JSONB가 유연성·트랜잭션 둘 다 준다.
- **샤딩 조기 도입** — 샤딩은 크로스샤드 JOIN/트랜잭션·리밸런싱·운영 복잡도를 폭증시킨다. **수직 확장 + read-replica + 파티셔닝을 먼저 소진**한 뒤 마지막에.
- **폴리글랏 남발** — DB 5종은 백업·모니터링·정합성 5벌. 각 추가에 "PG가 여기서 무너지는 임계는?"을 수치로 답하지 못하면 도입 보류.
- **캐시를 SoT로** — Redis에만 있는 데이터는 장애 시 소실. 캐시는 항상 SoT의 파생.
- **이중 쓰기(dual-write)** — 앱이 PG와 ES에 각각 쓰면 한쪽 실패 시 영구 불일치. Outbox/CDC로 단일 쓰기 → 비동기 전파.
- **분석을 OLTP에서** — 무거운 집계 쿼리가 운영 트랜잭션 리소스를 잠식. replica 또는 DW로 분리.
- **강일관성 오버슈트** — 피드·좋아요·검색에 전역 강일관성을 걸어 지연·비용 낭비. 최종일관성으로 충분한 곳을 구분하라.
