# 스케일링 & 무중단 마이그레이션 처방

> **스케일링은 "무엇을 확장할지"를 먼저 정하고, 마이그레이션은 "구를 절대 지우지 않는" 순서로 한다.** 확장의 첫 질문은 항상 "읽기가 병목인가, 쓰기가 병목인가"다 — 둘의 해법은 완전히 다르다. 스키마 변경은 "동시에 두 버전을 만족시키는" expand-contract가 유일하게 안전한 길이며, 파괴적 변경은 lock 회피가 성패를 가른다. 기준: PostgreSQL 16/17, Debezium 3.x, Citus 12/13, Vitess 21+ (2025~2026).

## 0. 확장 전 원칙 — 순서를 지켜라

**섣부른 샤딩은 조기 최적화 중 최악이다.** 대부분의 서비스는 아래 사다리의 앞쪽에서 끝난다. 한 칸씩 올라가고, 각 칸을 소진했는지 지표로 확인한 뒤 다음으로 간다.

| 단계 | 처방 | 소진 신호(다음으로) |
|---|---|---|
| 1 | **인덱스·쿼리 튜닝** (제일 먼저, 제일 싸다) | 슬로우 쿼리 없는데도 CPU/IO 포화 |
| 2 | **수직 확장(scale-up)** — 인스턴스 증설 | 최대 인스턴스 근접, 비용 비선형 급증 |
| 3 | **읽기 복제본 + 캐시** (읽기 병목이면 여기서 끝나는 경우 다수) | 쓰기 TPS·WAL 처리량이 primary 한계 |
| 4 | **파티셔닝** (단일 노드 내 대용량 테이블 분할) | 단일 노드 스토리지/쓰기 물리 한계 |
| 5 | **샤딩/분산(scale-out)** — 최후의 수단, 되돌리기 어려움 | — |

**황금률**: 읽기 확장은 쉽다(복제본을 늘려라). 쓰기 확장은 어렵다(샤딩은 아키텍처를 영구히 바꾼다). 샤딩을 검토하기 전에 3·4단계를 반드시 소진하라.

## 1. 스케일링 축 — 수직 vs 수평, 읽기 vs 쓰기

| 축 | 수직(scale-up) | 수평(scale-out) |
|---|---|---|
| 방법 | CPU/RAM/IOPS 증설 | 노드 추가로 분산 |
| 장점 | 코드 변경 없음, 즉시, ACID 유지 | 이론상 무한, 단일 장애점 분산 |
| 한계 | 물리 상한, 비용 비선형, 단일 장애점 | 앱·운영 복잡도 폭증, 크로스 노드 쿼리 비쌈 |
| 처방 | **1차 선택** — 갈 수 있는 데까지 | 수직이 소진되고 쓰기가 병목일 때만 |

- **읽기 확장(read scaling)**: 복제본·캐시로 해결. **상대적으로 쉽다** — 데이터는 그대로 두고 사본을 늘린다.
- **쓰기 확장(write scaling)**: 단일 primary가 모든 쓰기를 받는 구조는 복제본으로 못 푼다(복제본도 결국 같은 쓰기를 재생). **샤딩/파티셔닝**만이 답. 어렵고 비가역적.

## 2. 읽기 확장 — 복제본 · 풀링 · 캐시

### 2-1. 읽기 복제본 (read replica)

- primary → replica 스트리밍 복제. 읽기 쿼리를 replica로 라우팅해 primary 부하 경감. 복제본은 수평 추가 가능.
- **복제 지연(replication lag)이 핵심 함정**: replica는 primary보다 수 ms~수 초 뒤처진다. 부하·긴 트랜잭션·네트워크에 따라 지연이 튄다.

**read-your-writes 문제**: 사용자가 쓰기 직후 자기 데이터를 읽는데 요청이 lagging replica로 가면 **방금 쓴 게 안 보인다.** 처방:

| 전략 | 처방 |
|---|---|
| **read-your-writes 라우팅** | 쓰기 직후 N초간(또는 세션 동안) 해당 사용자 읽기를 primary로 |
| **LSN 추적** | 쓰기가 반환한 WAL 위치(LSN) 이상 적용된 replica로만 라우팅 |
| **유계 staleness** | `lag < 임계값`인 replica만 풀에 포함, 지연 큰 노드 자동 배제 |
| **강한 읽기 지정** | 결제·잔액 등 stale 불가 읽기는 명시적으로 primary |

**동기 vs 비동기 복제**: 비동기(디폴트)는 primary 성능 좋으나 장애 시 미복제 데이터 유실 가능. 동기(`synchronous_commit=on` + standby)는 유실 0이나 쓰기 지연↑·standby 장애 시 primary 정지 위험. 실무는 **quorum 기반 동기**(N개 중 과반 ack)로 절충.

### 2-2. 커넥션 풀링 (PgBouncer)

- PostgreSQL은 연결당 프로세스 → 수천 연결이면 메모리·컨텍스트 스위칭으로 붕괴. **앱 연결 수 ≫ DB 연결 수**를 풀러가 흡수.
- **PgBouncer 풀 모드**: `session`(연결 세션 단위) / `transaction`(**권장** — 트랜잭션 단위 재사용, 최고 효율) / `statement`(문장 단위, 위험).
- `transaction` 모드 주의: 세션 상태(prepared statement, `SET`, advisory lock, `LISTEN/NOTIFY`)에 의존하면 깨진다. 서버리스/고동시성에선 사실상 필수.
- 대안: pgcat, Supavisor(멀티테넌트·프로토콜 인지 풀러). 규모가 크면 풀러를 replica 앞에도 둔다.

### 2-3. 캐싱 계층

- DB 앞 Redis/Memcached로 hot read를 흡수 → 복제본조차 안 타게 한다. 캐시 패턴(cache-aside/write-through)·TTL·stampede 방지는 [nosql-modeling.md](./nosql-modeling.md) 4장 참조.
- **순서**: 캐시로 걸러지지 않는 읽기만 replica로, replica로 안 되는 것만 샤딩. 각 계층이 뒤 계층의 부하를 줄인다.

## 3. 쓰기 확장 / 샤딩

### 3-1. 파티셔닝 vs 샤딩 — 먼저 구분하라

| | 파티셔닝(partitioning) | 샤딩(sharding) |
|---|---|---|
| 위치 | **단일 서버 내** 테이블을 조각으로 | **여러 서버**에 데이터 분산 |
| 목적 | 쿼리 프루닝, 유지관리(대량 삭제) | 쓰기/스토리지 수평 확장 |
| 복잡도 | 낮음(DB 네이티브 기능) | 높음(라우팅·재분배·크로스샤드) |
| 트랜잭션 | 단일 노드 ACID 유지 | 크로스샤드는 분산 트랜잭션 필요 |
| 처방 | 대용량 테이블이면 거의 항상 먼저 | 파티셔닝으로도 안 될 때만 |

**결론**: 파티셔닝을 먼저 소진하라. 파티셔닝은 되돌리기 쉽고 앱 변경이 거의 없다. 샤딩은 비가역적이다.

### 3-2. 샤드 키 선택 — 샤딩의 90%가 여기서 결정된다

**잘못된 샤드 키의 대가는 전면 재샤딩(reshard)이며, 이는 서비스 최대 난이도 작업이다.** 4대 기준:

| 기준 | 요구 | 위반 시 |
|---|---|---|
| **높은 카디널리티** | 값 종류가 충분히 많아야 | 샤드 수보다 값이 적으면 분산 불가 |
| **균등 분포** | 값이 샤드에 고르게 | 편향 → 특정 샤드 과부하 |
| **핫스팟 회피** | 쓰기·읽기가 시간적으로 몰리지 않게 | `created_at`·auto-increment ID → 최신 샤드에 전부 집중 |
| **쿼리 라우팅** | 대부분 쿼리가 **단일 샤드로** 도달 | 샤드 키 없는 쿼리 → 전 샤드 팬아웃(scatter-gather) |

- **좋은 예**: `user_id`, `tenant_id`, `account_id` — 카디널리티 높고, 대부분 쿼리가 이 키를 포함(사용자별·테넌트별 격리).
- **나쁜 예**: `status`(저카디널리티·핫), `created_at`(단조 증가·최신 핫), 순차 ID(핫스팟). 이메일·랜덤 UUID는 균등하나 **범위 쿼리가 전 샤드 팬아웃**됨에 유의.
- **핵심**: 샤드 키는 **가장 빈번한 접근 패턴의 필터 컬럼**과 일치시켜라. 쿼리가 샤드 키를 포함하면 단일 샤드, 아니면 전 샤드 스캐터. 스캐터-개더 비율이 높으면 샤딩이 오히려 느리다.
- **되돌릴 수 없음**: 샤드 키는 나중에 바꾸기가 사실상 전체 데이터 재분배 = 무중단 재샤딩. 설계 단계에서 접근 패턴을 전부 나열하고 결정하라.

### 3-3. 샤딩 전략

| 전략 | 방식 | 장점 | 대가 |
|---|---|---|---|
| **Range** | 키 범위로 분할(A–M / N–Z, 날짜 구간) | 범위 쿼리 효율, 직관적 | **핫스팟**(최신 범위 집중), 수동 리밸런싱 |
| **Hash** | `hash(key) % N` 또는 해시 링 | 균등 분포, 핫스팟 적음 | 범위 쿼리 불가, **N 변경 시 대량 재배치** |
| **Consistent Hash** | 해시 링 + 가상 노드 | 노드 추가/제거 시 재배치 최소(1/N만 이동) | 구현 복잡, 여전히 범위 쿼리 약함 |
| **Directory** | 룩업 테이블이 키→샤드 매핑 관리 | 유연한 재배치, 임의 규칙 | 룩업이 단일 장애점·병목, 캐싱 필수 |
| **Geo** | 지역별 샤드(EU/US/APAC) | 지연↓, 데이터 주권(GDPR) 준수 | 지역 간 쿼리 비쌈, 이동 사용자 처리 |

**리샤딩의 고통**: hash % N에서 N을 늘리면 거의 모든 키가 재배치된다. 처방: ① **consistent hashing**으로 이동량을 1/N로 제한 ② **논리 샤드 과다 생성**(예: 1024개 논리 샤드를 소수 물리 노드에 매핑 → 노드 추가 시 논리 샤드만 이동, 재해시 없음. Vitess/Citus 방식) ③ 처음부터 여유 있게 샤드 수 설정.

### 3-4. 분산 확장 미들웨어

| 도구 | 기반 | 특징 |
|---|---|---|
| **Citus** | PostgreSQL 확장 | `distributed table`(해시 분산) + `reference table`(전 노드 복제) + `co-location`(같은 샤드 키끼리 로컬 조인). PG 네이티브 SQL 유지. 멀티테넌트·시계열 강점 |
| **Vitess** | MySQL 프록시 | VSchema로 샤딩 규칙 선언, **온라인 리샤딩**(라이브 트래픽 중 데이터 복사·검증 후 컷오버) 내장. YouTube 유래 |
| **CockroachDB / YugabyteDB** | 분산 SQL(NewSQL) | 샤딩·복제·재분배를 DB가 자동. 앱은 단일 DB처럼 사용(수동 샤딩 회피) |

**처방**: 수동 샤딩(앱에서 라우팅) 전에 위 도구를 검토하라. 재분배·크로스샤드 쿼리·2PC를 DB/미들웨어가 처리해 앱 복잡도를 크게 줄인다.

### 3-5. 분산 트랜잭션 & 크로스샤드 비용

- **크로스샤드 조인**: 조인 대상이 다른 샤드에 있으면 네트워크 팬아웃. 회피책 — **co-location**(연관 데이터를 같은 샤드 키로 묶어 로컬 조인), 참조 데이터는 전 노드 복제(reference table).
- **분산 트랜잭션 2PC(2단계 커밋)**: 여러 샤드에 원자적 쓰기. 강한 일관성이나 **느리고**(코디네이터 왕복), **코디네이터 장애 시 블로킹**, 가용성 저하. 고TPS 경로에선 회피.
- **Saga 패턴(권장)**: 분산 트랜잭션을 **로컬 트랜잭션 + 보상 트랜잭션(compensating)**의 연쇄로 대체. 강한 일관성 대신 최종 일관성 수용. 실패 시 앞 단계를 보상 액션으로 되돌린다. 대부분의 마이크로서비스 워크플로에 2PC보다 적합.
- **원칙**: 샤딩했으면 **크로스샤드 트랜잭션이 필요 없도록 샤드 경계를 설계**하라. 한 트랜잭션이 여러 샤드를 건드리면 샤드 키 선택이 잘못됐다는 신호.

## 4. 파티셔닝 상세

### 4-1. 파티션 종류

| 종류 | 기준 | 용도 |
|---|---|---|
| **Range** | 값 구간 | **시간 기반**(로그·이벤트·시계열) — 가장 흔함 |
| **List** | 명시적 값 목록 | 지역·카테고리·테넌트 등 이산 분류 |
| **Hash** | 해시 균등 분배 | 자연 파티션 키 없이 균등 분산만 원할 때 |

### 4-2. 시간 기반 파티셔닝 (대용량 로그·시계열의 정석)

- `created_at` 등으로 월/주/일 단위 range 파티션. 최근 파티션만 hot → **파티션 프루닝**으로 오래된 파티션 스캔 회피.
- **가장 큰 이득은 유지관리**: 오래된 데이터 삭제가 `DELETE`(느림·톰스톤·vacuum 부하) 대신 **`DROP PARTITION`/`DETACH`**(즉시, 거의 무비용). 대용량 롤오프(retention)의 핵심.
- **자동화**: PostgreSQL 네이티브 선언적 파티셔닝 + **pg_partman**으로 미래 파티션 사전 생성 + retention 자동 폐기. Citus와 결합 시 시계열을 분산 + 파티셔닝 동시 적용(IoT 표준 구성).
- **주의**: 파티션 키는 반드시 PK/유니크 제약에 포함되어야 한다. 크로스 파티션 유니크는 비쌈. 파티션 수가 수천 개면 플래닝 오버헤드 → 적정 입도 유지.

## 5. 무중단 스키마 마이그레이션 — expand-contract (핵심)

**단일 원칙: 구 코드와 신 코드가 동시에 돌 수 있는 스키마만 배포하라.** 앱과 DB를 한 번에 못 바꾸므로(롤링 배포 중 두 버전 공존), 모든 변경은 **하위 호환**이어야 한다. 파괴적 변경은 여러 릴리스로 쪼갠다.

### 5-1. expand-contract 4단계

| 단계 | 이름 | 하는 일 | 불변식 |
|---|---|---|---|
| 1 | **Expand** | 신 구조를 **추가만**(새 컬럼·테이블·인덱스). 기존 것 손대지 않음 | 구 코드가 그대로 동작 |
| 2 | **Dual-write / Backfill** | 앱이 **신·구 양쪽에 동시 기록** + 과거 데이터 배치 **백필** | 신·구가 수렴 |
| 3 | **Cutover** | 읽기를 신 구조로 전환, 정합성 **검증**(신==구 카운트/샘플) | 신이 진실의 원천 |
| 4 | **Contract** | 구 구조 **제거**(별도 릴리스로) | 아무도 구를 참조 안 함 |

**핵심 규율**:
- 각 단계는 **독립 배포**. 특히 Contract는 반드시 별도 릴리스 — 롤백 여지 확보. Expand와 Contract를 같은 배포에 넣으면 무중단이 깨진다.
- 각 단계 사이에 관측 기간을 둔다(에러율·정합성 모니터). 문제 시 다음 단계로 안 넘어가면 그대로 롤백 가능.
- **컬럼 rename**은 그 자체가 파괴적 → "새 컬럼 추가(expand) → dual-write → 백필 → 읽기 전환 → 구 컬럼 drop(contract)"으로 분해.

### 5-2. PostgreSQL 파괴적 변경의 안전 처리 — lock 회피

DDL은 `ACCESS EXCLUSIVE` lock을 잡으면 **읽기·쓰기 모두 대기** → 잠깐이라도 대량 트래픽이면 락 큐가 폭발한다. 핵심은 **락을 짧게, 못 잡으면 빨리 포기**.

| 변경 | 위험 | 안전 처방 |
|---|---|---|
| **인덱스 생성** | `CREATE INDEX`가 쓰기 블록 | **`CREATE INDEX CONCURRENTLY`** — 쓰기 차단 안 함. 단 트랜잭션 밖에서만 실행(마이그레이션 도구의 자동 트랜잭션 래핑 해제 필요), 실패 시 `INVALID` 인덱스 남으니 `DROP` 후 재시도 |
| **컬럼 추가(기본값)** | 구버전은 전체 테이블 재작성 | **PG 11+는 상수 기본값 add가 메타데이터만 변경(즉시)**. `volatile` 기본값(예: `now()`, `random()`)은 여전히 재작성 → 상수로 추가 후 백필 |
| **NOT NULL 추가** | 전체 스캔하며 락 | **① `CHECK (col IS NOT NULL) NOT VALID` 추가(즉시)** → **② `VALIDATE CONSTRAINT`(SHARE UPDATE EXCLUSIVE, 쓰기 허용)**. PG 18은 `NOT NULL ... NOT VALID` 직접 지원 |
| **컬럼 DROP** | 앱이 아직 참조하면 즉시 장애 | expand-contract의 **Contract 단계에서만**. 앱 배포로 참조 제거 확인 후 별도 릴리스. `DROP`은 메타데이터라 빠름 |
| **타입 변경** | 대개 전체 테이블 재작성 + 긴 락 | **직접 `ALTER TYPE` 금지.** 새 컬럼(신 타입) 추가 → dual-write → 백필 → 읽기 전환 → 구 컬럼 drop |
| **FK 추가** | 전체 검증하며 락 | `... NOT VALID`로 추가(신규 행만 검증) → 이후 `VALIDATE CONSTRAINT`(락 약함) |
| **컬럼 rename** | 구/신 코드 동시 만족 불가 | 직접 rename 금지 → 신 컬럼 추가 + dual-write + 백필 + 전환 + drop |

**모든 마이그레이션 공통 가드**:
```sql
SET lock_timeout = '2s';       -- 락 못 잡으면 대기 큐 막기 전에 실패
SET statement_timeout = '30s'; -- 폭주 방지
```
락 획득 실패 시 **에러로 빠지고 재시도**(exponential backoff). 무한 대기하며 뒤따르는 모든 쿼리를 막는 것보다, 짧게 실패하고 조용한 시점에 재시도하는 편이 무중단이다.

### 5-3. 대용량 백필 (batch + throttle)

- **단일 `UPDATE` 금지**: 수백만 행을 한 문장으로 갱신하면 회피하려던 DDL만큼 긴 락 + WAL 폭증 + 복제 지연 급증.
- **처방**: PK 범위로 **10K 이하 청크** 반복. 각 배치는 별도 트랜잭션 커밋. 배치 간 **sleep(throttle)**로 복제 지연·IO를 억제(replication lag 모니터링하며 동적 조절).
- 진행 상황을 **체크포인트**(마지막 처리 PK)로 저장 → 중단·재개 가능. `WHERE new_col IS NULL` 같은 부분 인덱스로 남은 행만 빠르게 스캔.
- 대안 도구: **pg-osc**(shadow table + 트리거로 스키마 변경·백필을 무중단화, MySQL의 pt-osc/gh-ost에 대응). 복잡한 파괴적 변경엔 수동보다 안전.

### 5-4. 롤백 전략

- Expand·Dual-write 단계는 **추가만** 했으므로 앱만 이전 버전으로 되돌리면 롤백 완료(스키마는 그대로 둬도 무해).
- **파괴적 단계(Contract) 전에는 항상 롤백 가능**해야 한다. 그래서 Contract를 마지막·독립 릴리스로 미룬다.
- 마이그레이션은 **가능한 한 되돌릴 수 있게**(reversible) 작성. 되돌릴 수 없는 단계(데이터 삭제)는 백업·검증을 선행.

### 5-5. 마이그레이션 안전성 등급표

| 변경 | 등급 | 절차 |
|---|---|---|
| nullable 컬럼 추가(기본값 없음/상수 PG11+) | **SAFE** | 바로 적용 |
| `CREATE INDEX CONCURRENTLY` | **SAFE** | 트랜잭션 밖, 실패 시 재생성 |
| `CHECK ... NOT VALID` 추가 | **SAFE** | 즉시, 이후 VALIDATE |
| 새 테이블 추가 | **SAFE** | 바로 적용 |
| `DROP` 컬럼/테이블 | **CAUTION** | 앱이 참조 제거된 뒤 Contract 단계에서만 |
| `NOT NULL` 추가 | **CAUTION** | NOT VALID CHECK → VALIDATE, 직접 SET NOT NULL 금지 |
| FK 추가 | **CAUTION** | NOT VALID → VALIDATE |
| 대용량 백필 | **CAUTION** | 배치 + throttle + 체크포인트 |
| 일반 `CREATE INDEX`(비CONCURRENTLY) | **DANGEROUS** | 쓰기 락 → CONCURRENTLY로 대체 |
| 컬럼 타입 변경 / rename | **DANGEROUS** | expand-contract로 분해 |
| `volatile` 기본값으로 컬럼 추가 | **DANGEROUS** | 상수 추가 + 백필로 분해 |
| 단일 문장 대량 `UPDATE`/`DELETE` | **DANGEROUS** | 배치로 분해 |

## 6. CDC & 데이터 동기화

### 6-1. Change Data Capture

- **CDC**: DB 변경(insert/update/delete)을 실시간 캡처해 하류 시스템(검색엔진·캐시·데이터레이크·다른 서비스)에 전파. 폴링 대비 지연↓·부하↓.
- **PostgreSQL 논리적 복제(logical decoding)**: WAL을 논리 변경 이벤트로 디코딩(PG 10+). **Debezium**이 이를 소비해 Kafka 등으로 스트리밍하는 표준 조합.
- **운영 필수 모니터링**: replication slot **lag**, WAL 처리량, 소비 지연. slot이 소비 안 되면 **WAL이 무한 축적 → 디스크 폭발**(운영 사고 1순위). 알림을 처음부터 건다.

### 6-2. Transactional Outbox 패턴 (이중 쓰기 해법)

- **이중 쓰기 문제**: DB 커밋 + 메시지 발행을 순차로 하면 하나만 성공 → 불일치. 두 시스템에 원자적으로 쓸 방법은 없다.
- **Outbox**: 비즈니스 데이터와 이벤트를 **같은 로컬 트랜잭션으로 outbox 테이블에 함께** 기록 → CDC(Debezium)가 outbox를 스트리밍해 브로커로 발행. 원자성 확보 + 발행 관심사 분리.
- **PG 진화형**: outbox 테이블 대신 **logical decoding message**를 WAL에 직접 emit → 테이블 청소(housekeeping) 불필요.
- Debezium 권장 메시지 필드: `id`(멱등 dedup용), `aggregate_type`, `aggregate_id`(파티션 키).

### 6-3. 이벤트 순서 · 멱등성 · 폴리글랏 전파

- **순서 보장**: 같은 엔티티의 이벤트는 순서가 뒤바뀌면 안 됨 → **엔티티 키(aggregate_id)를 파티션 키로** 하여 같은 파티션·같은 컨슈머로. 전역 순서는 비싸니 엔티티 단위 순서로 족하다.
- **멱등성**: CDC·메시지 브로커는 **at-least-once**(중복 배달 가능). 컨슈머는 `event_id` 기반 dedup 또는 **멱등 연산**(upsert, 조건부 갱신)으로 재처리에 안전해야 한다.
- **폴리글랏 저장소 전파**: RDBMS → 검색엔진(Elasticsearch/OpenSearch)·캐시·데이터웨어하우스로 CDC 전파. 각 하류는 최종 일관성. 원본과 파생본의 **동기화 지연 SLA**를 명시하고, 파생본을 진실의 원천으로 오인하지 말 것.

## 7. 용량 산정 (capacity planning)

| 항목 | 산정 |
|---|---|
| **행/문서 크기** | 컬럼 크기 합 + 오버헤드(PG 행당 ~24B 헤더 + 정렬 패딩). 실측이 정확 |
| **총 스토리지** | `행 크기 × 행 수 × (1 + 인덱스 오버헤드)`. 인덱스는 흔히 데이터의 **20~100%** 추가 |
| **성장률** | `일일 유입 행수 × 평균 크기 × 365` → 연 증가. TOAST(대형 값)·WAL·백업 별도 계상 |
| **IOPS** | 피크 TPS × 쿼리당 IO. 인덱스 없는 스캔은 IO 폭증 — 인덱스가 IOPS를 좌우 |
| **여유** | 피크의 **2~3배** 헤드룸. 디스크 사용률 **80% 넘기면 위험**(vacuum·정렬·임시파일 공간 부족) |

**아카이빙 / 콜드 스토리지**: hot 데이터만 primary에 유지, 오래된 데이터는 **시간 파티션 DETACH → 콜드 스토리지**(S3/객체 스토어, Parquet)로 이관. retention 정책을 파티션 DROP과 결합해 자동화. 조회 빈도 낮은 이력은 데이터레이크로, DB는 작고 빠르게 유지.
