# NoSQL 모델링 처방 (문서 / 키-값 / 와이드컬럼 / 인메모리)

> **쿼리부터 설계한다.** 관계형이 "엔티티 정규화 → 조인으로 재조립"이라면, NoSQL은 반대다 — 먼저 접근 패턴(access pattern)을 전부 나열하고, 데이터 모델을 그 쿼리에 물리적으로 맞춘다. 조인이 없거나 비싸므로, 함께 읽는 데이터는 함께 저장한다. 기준: MongoDB 7/8, Redis 8 / Valkey, DynamoDB, Cassandra 5.0 / ScyllaDB (2025~2026).

## 0. NoSQL 공통 원칙 — 관계형과 무엇이 반대인가

| 축 | 관계형 (RDBMS) | NoSQL |
|---|---|---|
| **설계 출발점** | 데이터 구조(정규화) 먼저 | **쿼리(접근 패턴) 먼저** |
| **중복** | 회피 (3NF) | 의도적 수용 (denormalization = 디폴트) |
| **조인** | DB가 처리, 저렴 | 없음 / 앱 레이어 / 비쌈 → 회피 설계 |
| **일관성** | 강함(ACID)이 디폴트 | 최종/튜너블이 디폴트, 강함은 옵션 |
| **스키마 진화** | 마이그레이션(DDL) | 필드 추가 무비용, 버전 필드로 흡수 |

**설계 절차(모든 NoSQL 공통)**: ① 접근 패턴 표 작성 — "무엇을, 어떤 키로, 얼마나 자주, 읽기/쓰기 비율" ② 각 패턴을 단일 쿼리로 만족시키는 물리 모델 역산 ③ 남는 패턴만 보조 인덱스/보조 테이블로 커버 ④ 쓰기 시 중복 동기화 비용 측정. **엔티티 다이어그램을 먼저 그리면 관계형 습관에 빠진다** — 접근 패턴 표가 원천이다.

**황금률**: "함께 읽으면 함께 저장, 따로 자라면 따로 저장." 나머지는 이 원칙의 응용이다.

## 1. 문서 DB (MongoDB, CouchDB)

### 1-1. Embed vs Reference — 결정 기준

가장 중요한 결정. 잘못 고르면 16MB 한계에 부딪히거나 조인 지옥에 빠진다.

| 관계 | 기본 처방 | 근거 |
|---|---|---|
| **1:1** | Embed | 항상 함께 조회, 원자 갱신 |
| **1:few** (상한 있는 소수, 예: 주소 3개) | Embed | 한 번의 읽기, 문서 크기 예측 가능 |
| **1:many** (수백~수천) | Reference (자식이 부모 참조) | 무한 성장 배열 회피 |
| **many:many** | Reference (양쪽 ID 배열 or 링크 문서) | 공유·독립 갱신 |

**Embed 선택 조건**: (1) 항상 함께 읽는다 (2) 성장이 유계(bounded)하고 작다 (3) 읽기:쓰기 비율이 높다 (4) 부분 갱신이 드물다. **Reference 선택 조건**: (1) 무계(unbounded) 성장 (2) 독립적으로 자주 갱신 (3) 여러 문서가 공유 (4) 실체가 단독 조회 대상.

**세 가지 하드 경계**:
- **16MB 문서 상한** — 임베드 배열이 여기 근접하면 이미 설계 실패. 실무 성능은 훨씬 이전(수백 KB)부터 저하.
- **원자성 경계** — 단일 문서 쓰기만 원자적. 원자 갱신이 필요한 데이터는 한 문서에 담아야 한다(멀티문서 트랜잭션은 4.0+에서 가능하나 비용·경합 발생).
- **갱신 빈도** — 큰 문서의 작은 필드를 자주 바꾸면 전체 문서가 메모리에서 재기록된다.

### 1-2. 공식 스키마 패턴

| 패턴 | 문제 | 처방 |
|---|---|---|
| **Extended Reference** | 참조마다 $lookup 반복 | 외부 문서에서 **자주 쓰는 필드 몇 개만** 복제 임베드 (예: `order.customer.{name,tier}`) |
| **Subset** | 문서에 hot/cold 데이터 혼재, 16MB 압박 | 자주 쓰는 부분집합만 본 문서에, 나머지(리뷰 전체 등)는 별도 컬렉션 |
| **Computed** | 매 읽기마다 무거운 집계 | 쓰기 시 미리 계산해 저장(합계·평균·카운트) |
| **Bucket** | 시계열·이벤트가 문서당 1건 → 문서 폭증 | 시간/개수 창으로 묶어 한 문서에 N개 (센서 1시간치 등). **무한 배열 방지의 정석** |
| **Outlier** | 소수 문서만 비정상적으로 큼(팔로워 1000만) | 예외 문서는 오버플로 컬렉션으로 분리, 플래그 필드 |
| **Schema Versioning** | 스키마 변경 시 전체 마이그레이션 부담 | `schemaVersion` 필드로 구버전·신버전 공존, 무중단 진화 |
| **Approximation** | 정확 카운트 비용 과다 | 근사값 허용(N번에 1번 갱신, HLL 유사) |
| **Polymorphic** | 유사하지만 필드가 다른 엔티티 | 한 컬렉션에 이종 문서 + `type` 판별 필드 |
| **Tree** | 계층 구조(카테고리, 조직도) | 부모 참조 / 자식 배열 / **조상 배열(array of ancestors)** — 조회 패턴에 맞춰 선택 |

### 1-3. 인덱스 & 집계 경계

- **인덱스 종류**: 단일 / **복합(compound)** / **멀티키(배열 자동 인덱싱)** / 텍스트(전문 검색) / **부분(partial, `{deleted:false}`로 크기 절감)** / 와일드카드(동적 필드).
- **복합 인덱스 ESR 규칙**: **E**quality → **S**ort → **R**ange 순서로 필드 배치. 예: `find(status=X).sort(createdAt).where(price>Y)` → `{status:1, createdAt:1, price:1}`. 이 순서라야 필터+정렬을 인덱스 하나로 커버.
- **집계 파이프라인 경계**: 스테이지당 **메모리 100MB** 한계 → 초과 시 `allowDiskUse:true`. 인덱스는 파이프라인 **선두의 `$match`/`$sort`/`$geoNear`**에서만 활용됨(뒤로 밀면 무용).
- **스키마 검증**: `$jsonSchema` validator로 필수 필드·타입·범위 강제. 유연 스키마라도 핵심 불변식은 DB에서 검증.
- **시계열 컬렉션**: `granularity`(seconds/minutes/hours) 또는 `bucketMaxSpanSeconds`(6.3+)로 자동 버킷팅 + 압축 + TTL. 시계열은 Bucket 패턴 수동 구현보다 이걸 우선.

### 1-4. 안티패턴

- **무한 성장 배열(unbounded array)** — `post.comments[]`에 무제한 append. 매 추가마다 문서 전체 재기록, 인덱스 팽창, 결국 16MB. → Reference 또는 Bucket으로 전환.
- **과도한 embed** — "조인 없애려고" 전부 임베드 → 문서 비대, 작은 갱신도 큰 쓰기, 부분 조회 시 낭비.
- **컬렉션 폭증** — 테넌트마다·날짜마다 컬렉션 생성 → 운영 불능. 파티션은 문서 필드로.

## 2. 키-값 DB (Redis, DynamoDB)

### 2-1. 키 네이밍 & 접근 패턴 기반 설계

- **네이밍**: `namespace:entity:id[:field]` — 콜론 구분, 소문자, 예: `prod:user:123:profile`, `prod:session:abc`. 키 생성 로직을 한 곳에 모으고 스키마를 문서화.
- **접근 패턴 → 키 설계**: "이 데이터를 무슨 키로 찾을 것인가"를 먼저 정하고 키를 만든다. 스캔(KEYS/SCAN 전체 순회)은 프로덕션 금지 — 항상 직접 키 조회 또는 인덱스 구조(Sorted Set 등)로 도달.

### 2-2. Redis 자료구조 — 언제 무엇을

| 구조 | 용도 | 특성 |
|---|---|---|
| **String** | 캐시, 카운터, 세션, 레이트리밋 | 원자 INCR/DECR, 바이너리 안전 |
| **Hash** | 객체(필드 있는 엔티티), 소형 객체 대량 | 작은 객체 메모리 효율 최고 |
| **List** | 큐/스택, 최근 활동 피드, 유계 컬렉션 | 양끝 push/pop O(1) |
| **Set** | 유일성 추적, 교집합/합집합, 소셜 그래프 | 무순서 유일값, 집합 연산 |
| **Sorted Set** | **리더보드/랭킹**, 점수 기반 시계열, 슬라이딩 윈도우 레이트리밋 | 점수 정렬, 범위 조회 효율 |
| **Stream** | 이벤트 소싱, 지속 메시지 큐, 소비자 그룹 | append-only 로그 + consumer group |
| **HyperLogLog** | 순 방문자 수(카디널리티 추정) | 오차 ~0.81%, 규모 무관 **고정 12KB** |
| **Bitmap** | 사용자 활동·리텐션 코호트, 이진 상태 | 512MB로 40억 비트, AND/OR/XOR |
| **Geospatial** | 위치·근접 검색 | GEOADD/GEOSEARCH 반경 조회 |
| **Bitfield** | 압축 정수 배열, 부분 비트 원자 연산 | 세밀 비트 조작 |

**선택 규칙**: 정확 카운트=String INCR / 순 카운트(대략)=HLL / 랭킹=Sorted Set / 존재여부·집합=Set / 이진 대량 상태=Bitmap / 큐(단순)=List, 큐(지속·재처리)=Stream.

### 2-3. DynamoDB Single-Table Design

**하드 리밋**: 아이템 **400KB**, GSI **20개**/테이블(증설 요청 가능), LSI **5개**(하드), LSI 아이템 컬렉션 **10GB**/파티션키값, 파티션당 **3000 RCU / 1000 WCU**.

**접근 패턴 우선 방법론**: ① 모든 접근 패턴 나열 → ② PK/SK로 주 패턴을 단일 쿼리로 → ③ 보조 패턴은 GSI로. Query(1건 파티션 대상)는 Scan(전체)보다 100~1000배 저렴 — Scan은 설계 실패 신호.

- **복합 키**: PK=파티션(해시, **높은 카디널리티·균등 분포 필수** — `status=ACTIVE` 같은 저카디널리티 금지). SK=파티션 내 정렬 → 범위 쿼리·계층 표현(`ORDER#2026#001`).
- **GSI vs LSI**:

  | | GSI | LSI |
  |---|---|---|
  | 키 | 완전 다른 PK/SK | 베이스 PK 공유, SK만 다름 |
  | 생성 시점 | 언제든 추가/삭제 | **테이블 생성 시에만** |
  | 크기 한계 | 없음 | 10GB/파티션키값 |
  | 용량 | 별도 프로비저닝 | 베이스 공유 |

- **Adjacency List(다대다·그래프)**: 노드와 엣지를 같은 테이블에 표현. PK=엔티티ID, SK로 관계 종류 구분(`USER#1 / GROUP#5`, `GROUP#5 / USER#1`). **역 인덱스(inverse GSI)**로 PK↔SK를 뒤집어 반대 방향 쿼리("이 그룹의 멤버들").
- **핫 파티션 회피 / write sharding**: 파티션당 1000 WCU 상한. 5000 writes/s면 최소 `ceil(5000/1000)=5` 샤드. 파티션 키에 랜덤 접미사(1~N) 부여로 분산(안전 시작 N=10~16). 시간 버킷팅·캐싱·버퍼링 병행.
- **Single vs Multi-table (2025 실용주의)**: 2021~24년의 "무조건 단일 테이블" 도그마는 완화됨. **핵심 운영 테이블은 단일 테이블 설계, 수명주기가 다른 엔티티는 별도 테이블**로 나누는 2~5개 하이브리드가 테스트·추론·접근패턴 누락 리스크 측면에서 현실적. 온디맨드 가격이 2024.11 50% 인하되어 대부분 워크로드가 온디맨드로 저렴.

## 3. 와이드컬럼 (Cassandra, ScyllaDB, HBase)

### 3-1. 파티션 키 + 클러스터링 키 설계 (가장 중요)

와이드컬럼 설계의 90%는 여기서 결정된다.

- **파티션 키**: 데이터가 어느 노드에 저장될지 결정(일관된 해싱). **높은 카디널리티 필수** — 저카디널리티는 데이터·트래픽을 소수 노드에 집중(핫스팟). 쿼리당 조회 파티션 수를 최소화하도록 설계.
- **클러스터링 키**: 파티션 **내부 행 정렬** 기준. 범위 쿼리·정렬 효율의 원천. 예: `PRIMARY KEY ((user_id), created_at DESC)` — user_id로 파티셔닝, 최신순 정렬.

**"쿼리당 테이블 하나(one-table-per-query)"**: 조인이 없으므로 각 접근 패턴마다 그에 최적화된 테이블을 **중복 생성**한다. 같은 데이터가 3개 쿼리에 쓰이면 3개 테이블에 비정규화 저장. 쓰기가 조인보다 싸다는 전제.

### 3-2. 와이드/핫 파티션 회피 + 시간 버킷팅

- **파티션 크기 경계**: 실무 상한 **~100MB 또는 10만 행**, **이상적 10MB 미만**. 초과 시 JVM GC 정지, 읽기/쓰기 지연, 컴팩션 지연.
- **시간 버킷팅**: 무계 성장 파티션을 시간으로 쪼갠다. `(user_id)` 대신 `((user_id, day), ts)` — 고볼륨은 일 단위, 저볼륨은 월 단위. 이것이 와이드 파티션 방지의 정석.
- **핫 파티션**: 특정 파티션에 쓰기 집중 → 복합 파티션 키·버킷·랜덤 접미사로 분산.

### 3-3. 튜너블 일관성 & 톰스톤

- **일관성 레벨** (R+W>N이면 강일관성):

  | 레벨 | 범위 | 일관성 | 용도 |
  |---|---|---|---|
  | ONE / LOCAL_ONE | 1 복제본 | 최종 | 캐시성, staleness 허용 |
  | **LOCAL_QUORUM** | 로컬 DC 과반 | 강함 | **프로덕션 권장**(강일관성+합리적 지연) |
  | QUORUM | 전체 DC 과반 | 강함 | 멀티 DC 강일관성 필수 |
  | ALL | 전체 복제본 | 최강 | 드묾, 가용성 리스크 |

- **톰스톤(tombstone) 문제**: 삭제·TTL 만료는 데이터를 즉시 지우지 않고 **삭제 마커(톰스톤)**를 남긴다. `gc_grace_seconds` 기본 **864000초(10일)** 경과 후 컴팩션에서 제거. 임계값: `tombstone_warn_threshold` **1000**(경고), `tombstone_failure_threshold` **100000**(쿼리 중단, `TombstoneOverwhelmingException`). **고삭제·큐 패턴 안티**: 삭제가 잦은 테이블은 톰스톤 누적으로 읽기가 붕괴 → TimeWindowCompactionStrategy, gc_grace 튜닝, 애초에 삭제 대신 TTL+시간 버킷 파티션 폐기.
- **Cassandra 5.0**: **SAI(Storage-Attached Index)** — SSTable별 인덱스, 기존 2i보다 쓰기 증폭 적고 범위/텍스트 필터 지원. **벡터 검색**(vector 타입 + ANN, HNSW) 내장.
- **ScyllaDB**: CQL·프로토콜 호환. C++/Seastar shard-per-core로 **처리량 4~10배**, P99 서브밀리초 일관, tablets 아키텍처로 스케일링 효율 개선. Cassandra 튜닝 난제(JVM GC)를 상당 부분 제거.

## 4. 인메모리 (Redis, Memcached)

### 4-1. 캐시 패턴

| 패턴 | 흐름 | 트레이드오프 |
|---|---|---|
| **Cache-Aside(Lazy)** | 앱이 캐시 먼저 조회 → 미스 시 DB 읽고 캐시 채움 | 가장 흔함. 미스 시 **stampede** 위험 |
| **Read-Through** | 캐시 라이브러리가 미스 시 자동 로드 | 앱 로직 단순, 벤더 종속 |
| **Write-Through** | 쓰기가 캐시 → 동기적으로 DB까지 | 쓰기 지연↑, 강한 캐시-DB 일관성 |
| **Write-Behind** | 캐시에 즉시 쓰고 DB는 비동기 | 쓰기 지연↓, 캐시 유실 시 데이터 손실 위험 |

### 4-2. TTL·무효화·stampede 방지

- **TTL 전략**: 모든 캐시 키에 TTL 부여(무한 성장 방지). **지터(jitter)** 필수 — 동일 TTL은 동시 만료 → thundering herd. `TTL ± random(0~10%)`.
- **캐시 무효화**: 쓰기 시 해당 키 삭제(write-invalidate) 또는 갱신(write-through). "캐시 무효화는 컴퓨터 과학 2대 난제" — 무효화 키 범위를 좁게, 태그/버전 키로 일괄 무효화.
- **Stampede / thundering herd 방지**: (1) **분산 락(SETNX + 짧은 TTL)** — 한 요청만 재계산, 나머지 대기 (2) **확률적 조기 만료(XFetch)** — TTL 80% 지점에서 확률적으로 미리 갱신 (3) **요청 코얼레싱** — 동일 키 재계산은 한 번만.
- **캐시 워밍**: 배포·재시작 후 콜드 캐시를 사전 적재(핵심 키 배치 로드)해 초기 미스 폭주 방지.

### 4-3. 지속성 & Redis vs Memcached

- **지속성(RDB vs AOF)**: RDB=스냅샷(오버헤드 0에 가까움, 복구 빠름, 시점 손실 가능) / AOF=명령 로그(강한 내구성, 복구 느림, 파일 큼). **하이브리드(`aof-use-rdb-preamble yes`)가 프로덕션 권장** — RDB 프리앰블+최근 AOF로 빠른 복구+내구성. AOF fsync: `everysec`(권장, 최대 1초 손실) / `always`(느림) / `no`.
- **Redis vs Memcached**:

  | 선택 | 조건 |
  |---|---|
  | **Redis / Valkey** | 자료구조, 지속성, pub/sub, 스트림, 트랜잭션, 복잡 연산 필요 (대부분의 경우) |
  | **Memcached** | 순수 KV 캐시, 멀티코어 활용, 최소 메모리 오버헤드, >1MB 객체 |

- **라이선스 주의(2025)**: Redis 8.0+는 AGPLv3 또는 SSPL/RSAL 트라이라이선스. 완전 개방 필요 시 Linux Foundation의 **Valkey**(7.2.4 BSD 포크, AWS/Google/Oracle 후원)가 CQL 호환 드롭인.

## 5. NoSQL에서의 정합성 — 중복의 대가

NoSQL은 중복을 수용하는 대신 **동기화 책임을 앱이 진다.** 이 비용을 무시하면 조용히 데이터가 갈라진다.

- **이중 쓰기 문제(dual-write)**: DB + 메시지큐(또는 캐시 + DB, 테이블 A + 테이블 B)를 순차로 쓰다 하나만 성공 → 불일치. 두 시스템에 원자적으로 쓸 방법은 없다.
- **Transactional Outbox 패턴(권장 해법)**: 비즈니스 데이터와 이벤트를 **단일 트랜잭션으로 outbox 테이블에 함께** 기록 → 별도 프로세스가 outbox를 폴링/스트리밍해 브로커로 발행. 원자성 확보 + 발행 관심사 분리.
- **CDC / Change Streams**: **DynamoDB Streams**(→Kinesis 팬아웃), **MongoDB Change Streams**(insert/update/delete watch), **Cassandra CDC**. 폴링 대비 지연 제거·운영 단순화. 비정규화 복제본 동기화의 표준 수단.
- **애플리케이션 레벨 조인 비용**: 엔티티 A 조회 → ID로 B 조회 = 2 라운드트립. 팬아웃 시 N개 = N 쿼리. 읽기가 잦으면 **자주 함께 읽는 필드를 Extended Reference로 임베드**해 조인 자체를 제거(스토리지↔지연 트레이드오프).
- **비정규 데이터 동기화**: 원본 갱신 시 모든 복제본을 (가능하면 테이블 트랜잭션으로) 갱신하거나, CDC/Outbox로 최종 동기화. **동기화되면 안 되는 스냅샷**(주문 시점 가격 등)과 **동기화해야 하는 캐시 값**(작성자 이름)을 설계 시 명확히 구분한다.
